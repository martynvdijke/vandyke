## Context

The server is a single Go binary with `net/http`, an embedded SQLite database and server-rendered templates, enhanced with a vendored HTMX 2.0.11 and one hand-written script, `internal/web/static/js/app.js`. The public routes are registered in `internal/web/web.go`: `GET /{$}`, `/stats`, `/entries`, `/e/{id}`, `/feed.xml`, `POST /entries`, `/robots.txt`, `/sitemap.xml`, `/site.webmanifest` and `/static/`. The JSON API in `internal/httpapi/api.go` registers `GET /api/v1/entries`, `GET /api/v1/entries/{id}`, `POST /api/v1/entries`, `GET /api/v1/entries/{id}/photo`, `GET /api/v1/stats`, `GET /api/v1/persons` and `/healthz`.

All reads go through `internal/store/store.go`. `ListEntries` builds one `ledgerFilter` predicate that always starts with `e.deleted_at IS NULL` and adds the query grammar, the photo filter, the year and date bounds and `e.person = ? COLLATE NOCASE`. `Persons` and `PersonCounts` group or order on `person COLLATE NOCASE`. `Stats` counts distinct non-empty words with `word COLLATE NOCASE`. `GetEntryPhotoSize` serves the `thumb` and `display` variants, falling back to the original when a derivative is missing.

The HTML ledger is one `ledgerData` view model rendered by the `ledger` fragment in `partials.html`. Its sort, pager and clear-search URLs are built by `SortHref` and `PageHref`, which currently hardcode `/entries`, and the shared toolbar in `base.html` posts with `hx-get="/entries"`. The CSP set in `cmd/vandyke/main.go` allows scripts only from `'self'` and the configured Umami origin, so no inline script is possible and every behaviour lives in `app.js`. Native `<dialog>` elements already carry the add and info dialogs, opened by `data-dialog-open` and closed by `data-dialog-close`.

## Goals / Non-Goals

**Goals:**
- Let a reader walk the corpus by spelling, by person and by chance.
- Make the photographs the pipeline already stores browsable at thumbnail size, with the display image only on demand.
- Keep every page server-rendered, keyboard accessible and usable with JavaScript disabled.
- Reuse the existing store predicates, pagination helpers, Atom builder and dialog conventions rather than adding parallel ones.
- Keep trashed entries out of every new surface.

**Non-Goals:**
- Changing search ranking, the trigram index or the query grammar.
- Tags, categories, collections or any new metadata on entries.
- Admin curation of the index: no merge, hide or rename action.
- A third-party lightbox, masonry or infinite-scroll library.
- A schema change; no migration is required for any of the new reads.
- Changing the dedupe rule or the photo derivative sizes.

## Decisions

1. **The word index groups in SQL and buckets in Go**: `WordIndex` runs one grouped query over live entries with a non-empty `word`, grouped by `word COLLATE NOCASE`, returning the count, the earliest and latest `created_at`, and the newest occurrence's id and spelling. The page assigns each group to a letter bucket in Go by upper-casing its first rune: A–Z stay, anything else — digits, punctuation, accented and non-Latin scripts that fall outside A–Z — goes to `#`. SQLite's `NOCASE` folds only ASCII, which is exactly the identity the unique `(word, meaning)` index enforces, so grouping here agrees with dedupe and with `Stats.UniqueWords`; re-implementing the fold in Go would drift at the edges.

2. **The rail is fixed and one bucket renders per page**: the rail always shows A–Z plus `#` with a count per bucket, and empty letters render as inert, `aria-disabled` text so the index does not reshuffle as the corpus grows. `/words` renders exactly one bucket — `#` when it holds rows, otherwise the first non-empty letter — unless `?letter=` names another. Choosing one bucket per document keeps the page bounded and gives every bucket a stable URL without inventing a route for `#`. A ledger with no words renders the rail and a stated empty index rather than a 404; an explicit `?letter=` for a bucket with no rows is a 404, because the rail never links to one.

3. **Long letters paginate at 200 rows per page**: a letter page takes `?letter=F&page=2` and reuses `buildPageLinks` for the numbered pager. 200 is deliberately larger than the ledger's 30–100 choices because a word row is a single text line with no thumbnail, and a dictionary letter should be skimmable in as few pages as possible.

4. **Photo-only entries are not in the rail**: a row is listed only when its `word` is non-empty. The page instead carries one note, shown only when the count is non-zero, stating how many slips have only a photograph, linking to `/photos`. This keeps `#` meaning "starts with something that is not a letter" rather than doubling as a bucket of empty strings. One consequence is worth stating: the unique `(word, meaning)` index treats `('', '')` as a single key, so the ledger can hold at most one fully textless entry — the note counts what exists and promises no more.

5. **A word row links to the newest occurrence's permalink**: the row shows the spelling, its count, and its first and last date, and the spelling links to `/e/{id}` for the newest entry in the group. A second link into a filtered ledger would drag the query grammar and its quoting rules into a navigation page, and a spelling containing `-` or `"` would need escaping rules of its own.

6. **Person pages resolve case-insensitively and canonicalise to the newest spelling**: `GET /p/{person}` passes the decoded path value to `ListEntries` as `ListParams.Person`, which already compares with `person = ? COLLATE NOCASE`. A new `PersonProfile` read returns the displayed spelling, the total count, and the first and last slip for the whole case-insensitive group, or `store.ErrNotFound` when no live entry matches; the handler renders the existing not-found page on that error. Canonical, feed and navigation URLs are built from the returned spelling with `url.PathEscape`, so `/p/marieke` and `/p/Marieke` are one document with one canonical URL, and a name containing `/` survives as `%2F`.

7. **The person page keeps its scope in every control**: the page renders the same `ledger` fragment by setting a base path on `ledgerData` and on the toolbar. `SortHref`, `PageHref`, the clear-search link and the toolbar's `action` and `hx-get` all use that base path instead of the literal `/entries`. A `person` query parameter is ignored on a person page — the path wins — and the toolbar's person `<select>` is replaced by a static chip, because a control that silently widens the scope is worse than no control.

8. **The person feed is `/p/{person}/feed.xml`, not `/feed.xml?person=`**: the site feed's Atom `id` is `{base}/feed.xml`, so serving a different document from that id under a query parameter would be invalid Atom, and `/feed.xml` has a documented contract of `limit` only that existing readers and the README rely on. A child URL carries its own `id`, its own ETag, its own cache entry, and resolves under the person's canonical path. The feed reuses the builder in `internal/web/feed.go` with the same 1–100 `limit` clamp, `Cache-Control: public, max-age=60` and 304 on a matching `If-None-Match`, with the person included in the tag and the entry set filtered by `ListParams.Person`.

9. **Random lives at `/random` and `/api/v1/random`, never under an id path**: `GET /e/{id}` and `GET /api/v1/entries/{id}` parse a numeric id and answer not-found or `invalid_id` for anything else. A `random` segment placed under either would be matched by the `{id}` pattern and answered by the permalink handler as missing; registering a literal `GET /e/random` would only work because the Go 1.22 mux prefers a literal over a wildcard, carving a non-id token out of a namespace documented as numeric. Sibling paths leave both contracts intact, and `GET /api/v1/entries/random` keeps answering `400 invalid_id` instead of becoming a second way to ask for a random entry. `GET /random` answers `303 See Other` to `/e/{id}` — the status the create flow already uses to hand a client to a GET — so the permalink stays the one canonical document and a reload does not reroll. `GET /api/v1/random` returns the same entry object as `GET /api/v1/entries/{id}` with `Cache-Control: no-store`. Both accept only `photo` and `person`, and answer 404 when nothing matches, including on an empty ledger.

10. **The gallery pages by cursor, not by page number**: `GET /photos?cursor=<token>` walks entries that have a photo, newest first, 24 per batch. The token is the URL-safe base64 of the last tile's stored `created_at` and `id` joined by `_`, and the next batch selects `e.created_at < ? OR (e.created_at = ? AND e.id < ?)` after it. Page numbers would shift as entries are added, which repeats or skips tiles part-way through a scroll; a `(created_at, id)` cursor cannot, because a new row can only land above it. A malformed cursor answers 400 rather than silently restarting, which would loop the sentinel forever. `ListPhotoEntries` reuses `e.deleted_at IS NULL` and the `EXISTS (SELECT 1 FROM entry_photos …)` predicate, and reads only the thumb variant.

11. **Infinite scroll is a real link first**: the sentinel is `<a href="/photos?cursor=T" hx-get="/photos?cursor=T" hx-target="this" hx-swap="outerHTML" hx-trigger="revealed">`. HTMX swaps it for the next batch and a fresh sentinel; without HTMX the same URL is a complete document showing that batch with `rel="prev"` and `rel="next"` links. The handler returns the fragment only when `HX-Request` is present, matching `handleLedger`, and sets `Vary: HX-Request` so a shared cache cannot hand a fragment to a plain navigation. The last batch renders a closing line instead of a sentinel.

12. **One lightbox dialog, filled on open**: each tile is an `<a href="{photoURL}?size=display">` wrapping an `<img src="{photoURL}?size=thumb" loading="lazy" decoding="async">`, with `data-lightbox-src`, `data-lightbox-alt` and `data-lightbox-caption` on the anchor. A single `<dialog id="photo-lightbox">` per page holds one `<img>`; `app.js` copies the attributes into it and calls `showModal()` only when the dialog opens, so a grid of off-screen tiles never fetches a display image. The native dialog supplies Esc, the focus trap and the backdrop; the close handler returns focus to the anchor that opened it. Without JavaScript the anchor is an ordinary link to the display image.

13. **Alt text comes from the entry, not from the file**: a tile's alt text is `<word> → <meaning>` when both are present, the word alone when the correction is empty, and "Photograph attached to entry #0042" when the entry has no text, following the existing `alt` wording in the ledger fragment. Captions repeat the entry number, the date and the person when one is recorded.

14. **Navigation and indexing are explicit**: the shared masthead in `base.html` gains `Words` and `Photos` after `Stats`, and the footer gains both; the permalink's standalone header mirrors them because it does not use the shared masthead. `/words` and `/photos` are indexable and join the sitemap after `/stats`. `/p/{person}` is `noindex, follow` and stays out of the sitemap: it is the ledger filtered by one field, its rows are already in the sitemap as permalinks, and one near-identical document per attributed name would multiply the index. The `?letter=`, `?page=` and `?cursor=` variants are `noindex, follow` too, with the bare page as canonical. `/random` is not in the sitemap and its 303 carries `X-Robots-Tag: noindex`; robots.txt is not changed, because disallowing `/random` would stop a crawler reading that header.

15. **No migration**: every read is served by columns that already exist, and the indexes the new queries need are already in place — `idx_entries_word`, `idx_entries_person` and `idx_entries_created_at`, with `entry_photos.entry_id` as the primary key. The corpus is small — the embedded snapshot holds 78 entries — so the grouped word query and `ORDER BY RANDOM()` are cheap enough to run per request without new covering indexes.

## Risks / Trade-offs

- **[Word index cost]** -> one grouped query per page rather than one per letter; the group is covered by `idx_entries_word` and the corpus is small.
- **[ASCII-only case folding]** -> `NOCASE` does not fold `É` against `é`, so an accented spelling can appear as two rows; the index folds exactly as dedupe does, so the two surfaces never disagree, and the duplicate is visible rather than silently merged.
- **[Only one fully textless entry can exist]** -> the unique `(word, meaning)` index makes `('', '')` a single key, so the "photo-only" note can only ever count one row today; the gallery is the surface that shows all photographs, and the note does not promise per-photo rows.
- **[Person names containing a slash]** -> `ValidatePerson` permits them; links use `url.PathEscape` and the handler reads the decoded path value, so `%2F` resolves to the right person, but a hand-built `/p/a/b` URL does not.
- **[Person pages are excluded from search]** -> they exist for readers and for sharing, and every row links to a permalink that is indexed and in the sitemap.
- **[`ORDER BY RANDOM()` scans the table]** -> one scan per random request; the embedded snapshot holds 78 entries and a self-hosted ledger grows slowly, so a scan is cheap, while a count-plus-offset alternative needs two queries and still races with inserts.
- **[A person page that keeps the literal `/entries` toolbar]** -> the first keystroke would drop the person filter; the base path is threaded through the toolbar and the ledger links, and a test pins it.
- **[Gallery scroll repeats or skips tiles]** -> the cursor is a `(created_at, id)` pair, so a concurrently added entry can only appear above the cursor and is never repeated below it.
- **[Display images fetched for off-screen tiles]** -> the grid's `img` sources are thumb URLs only and the dialog sets the display URL on open; without JavaScript the reader explicitly follows a link to the display image.
- **[Lightbox focus loss]** -> the opening anchor is remembered and refocused on close, and the native dialog handles Esc and trapping.
- **[Malformed cursor breaks the scroll]** -> a malformed token is a 400 rather than a restart, so a bad bookmark is visible instead of looping.
- **[The ledger's person picker lists one name twice]** -> `Persons` selects distinct `person` values without folding case, so `Marieke` and `marieke` appear as two options that filter the same rows, while `PersonCounts` groups them with `COLLATE NOCASE`; the new profile read groups the same way and the person page canonicalises to one spelling, so the duplicate option leads to the same page and the picker is left unchanged to avoid altering the existing filter behaviour in this change.
- **[Random redirect caching]** -> `303` with `Cache-Control: no-store` and `X-Robots-Tag: noindex` keeps proxies and crawlers from turning `/random` into a fixed document.
