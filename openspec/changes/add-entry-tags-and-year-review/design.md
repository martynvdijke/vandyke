## Context

`entries` is the only content table: `id`, `word`, `meaning`, `person` (added by `008_entry_person.sql`), `created_at` and a nullable `deleted_at` (`009_entry_trash.sql`). `007_dedupe_entries.sql` collapsed duplicate rows and created `idx_entries_word_meaning` on `(word COLLATE NOCASE, meaning COLLATE NOCASE)`, so a spelling and correction pair can exist once. `entries_fts` is an FTS5 trigram index over `word`, `meaning` and `person`, maintained by hand on create, update, restore, seed and rebuild; trashed rows are removed from the index and reindexed on restore.

Reads funnel through `ListEntries`/`ledgerFilter` in `internal/store/store.go`, which builds `e.deleted_at IS NULL` plus the `q` branch, `photo`, `year`, `from`/`to` and exact `person` clauses. `Stats` computes totals, `unique_words` (`COUNT(DISTINCT word COLLATE NOCASE)`), first and last dates, the photo count, `ByYear` and the top eight persons. The web UI parses its own parameters in `parseListParams` (`internal/web/web.go`) and the API parses its own in `handleListEntries` (`internal/httpapi/api.go`); both feed `store.ListParams`. `handleFeed` (`internal/web/feed.go`) serves `GET /feed.xml` with ETag `"feed-<newestID>-<length>"` and `Cache-Control: public, max-age=60`; `handleSitemap` emits the home page, `/stats` and every live `/e/{id}`. Admin routes sit behind `requireAuth`, `withCSRF` or `withOwnerCSRF` (`internal/admin/admin.go`), mutations call `auditAs`, and `admins.username` is matched with `COLLATE NOCASE` at query time while unique indexes elsewhere use the `COLLATE NOCASE` index form (`idx_entries_word_meaning`, `idx_entries_person`). Foreign keys are enabled on the connection (`_pragma=foreign_keys(1)`), so cascades are real.

## Goals / Non-Goals

**Goals:**
- Give entries a tag vocabulary that an admin curates and assigns, without touching the dedupe rule or the search index.
- Let `tag` compose with every existing list filter on both the web page and the JSON API, with one query builder.
- Give each tag a canonical, countable, linkable public page and a feed view.
- Render one year of the ledger as a stable page with a shareable URL, no JavaScript and no stored aggregates.
- Keep trashed entries out of every new count, list, feed, sitemap entry and recap.

**Non-Goals:**
- Classifying existing entries automatically or asking the public to tag.
- Tag hierarchies, aliases, merges or per-tag permissions.
- Changing `(word, meaning)` uniqueness or deriving repetition counts from tags.
- Bulk tag assignment from the admin entries list.
- Tags in the JSON entry payload.
- Stored yearly aggregates, recap images or per-month recap pages.

## Decisions

1. **Two tables with a composite key and explicit indexes**: `014_entry_tags.sql` creates `tags(id, name, slug, color, created_at)` with `CREATE UNIQUE INDEX idx_tags_name ON tags (name COLLATE NOCASE)` and `CREATE UNIQUE INDEX idx_tags_slug ON tags (slug COLLATE NOCASE)`, plus `entry_tags(entry_id, tag_id, created_at, PRIMARY KEY (entry_id, tag_id))` with `REFERENCES entries(id) ON DELETE CASCADE` and `REFERENCES tags(id) ON DELETE CASCADE`. The primary key covers entry-to-tag lookups; `CREATE INDEX idx_entry_tags_tag ON entry_tags (tag_id, entry_id)` covers filtering and counting by tag. A single `entries.tags` text column would need parsing in SQL, cannot be counted without a scan, and cannot cascade on tag delete.

2. **The seed taxonomy is five tags inserted by the migration**: `typo`, `misheard`, `autocorrect`, `name`, `dialect`, each with a fixed muted colour (`#8c3b3b`, `#3b5a8c`, `#3b7a57`, `#8c6b3b`, `#6b3b8c`) and no assignments. They are the vocabulary the committee already uses, and an empty `/tags` on first boot would make the new page look broken. Because the seed is part of migration `014` it runs exactly once, guarded by `schema_migrations`, so a renamed seed keeps its new name and a deleted seed is not recreated on restart. Seeding assigns nothing: no entry is classified by the migration, and the seed is removable like any other tag.

3. **Slug is immutable, name is not**: the slug is derived from the name at creation (lowercase, ASCII letters and digits kept, every other run collapsed to one `-`, trimmed) and is what `?tag=` and `/tags/{slug}` use, so renaming a tag never breaks an existing link. Renaming changes `name` only. `ValidateTag` enforces a name of 1 to 40 runes, a slug that is non-empty after derivation, and a colour matching `#RRGGBB`; violations re-render the admin form with 422, matching `renderEditError`.

4. **The tag filter is one `EXISTS` clause per requested tag inside `ledgerFilter`**: `ListParams` gains `Tags []string`, and for each slug the builder appends `e.id IN (SELECT et.entry_id FROM entry_tags et JOIN tags t ON t.id = et.tag_id WHERE t.slug = ? COLLATE NOCASE)` with the slug as its argument. `ledgerFilter` already starts with `e.deleted_at IS NULL`, so a trashed entry can never match. Because every other filter is a separate clause joined with `AND`, tags intersect with `q`, `from`/`to`, `year`, `photo` and `person`, and two `tag` values intersect with each other. The FTS expression and the `LIKE` fallback are untouched: tags are a filter, not search text, so `entries_fts` gains no column and no reindex is required.

5. **Tags stay out of `store.Entry`**: the JSON shape of `GET /api/v1/entries` is unchanged, so no client has to handle a new field, and `store.Entry` keeps one meaning across the store, the API and the templates. The web layer needs chips per row, so `TagsByEntry(ctx, ids)` returns `map[int64][]store.Tag` in one query for the visible page instead of one query per row; the permalink and the admin edit form call `EntryTags(ctx, id)`. A new `tagOption` view type carries name, slug, colour and selected state for the edit form.

6. **Assignment replaces the whole set and only the admin can do it**: `SetEntryTags(ctx, entryID, tagIDs)` deletes the entry's rows and inserts the submitted set in one transaction, deduplicating ids. `handleUpdate` calls it after `UpdateEntry` succeeds and reads the submitted checkboxes from `r.PostForm["tags"]`, because the edit form is multipart. An empty submission clears every tag, which is the only way to untag without a second control. `POST /entries` and `POST /api/v1/entries` are unchanged and create untagged entries; tags on a trashed entry survive restore and disappear only when the entry is purged, because `PurgeEntries` deletes the `entries` row and the join rows cascade.

7. **Public surfaces are the index, the canonical tag page and the filter**: `GET /tags` lists every tag with its live count, including zero, because it is the taxonomy index and a freshly created tag must be reachable; `GET /tags/{slug}` renders the ledger for one tag through the existing `ledger-toolbar` and `ledger` partials, so `q`, `from`/`to`, `year`, `photo`, `person`, sort and pagination all keep working, with `tag` carried as a hidden field. `GET /entries?tag=` and `GET /api/v1/entries?tag=` are the documented filter forms. An unknown slug is not an error: the filter views return 200 with an empty result, exactly like `person=nobody`, while `/tags/{unknown}` returns 404 because it is a page for a named resource. A `/tags/{slug}` page whose entries are all trashed still returns 200 with the empty state, and the sitemap does not advertise it. Unlike a person page, which the planned `add-ledger-browse` change keeps out of the index because there can be one near-duplicate document per attributed name, a tag page is indexable: the vocabulary is curated by an admin, bounded to a handful of tags, and each page answers a distinct question about the ledger rather than repeating a field value.

8. **Canonicalisation is explicit and does not compete with `noindex`**: `/tags/{slug}` is standalone and emits `<link rel="canonical">` for itself; `page-head` gains a `CanonicalURL` field that renders the link only when set, and only standalone pages set it. `/entries` in every form, including `?tag=`, stays `noindex,follow` with no canonical link, following the policy set by `add-daily-slip-and-sharing`: a `noindex` page that also declares a canonical elsewhere sends conflicting signals to a crawler, and the sitemap never lists query-string URLs. The tag page is the indexable document and the filter view is not, so nothing competes. Sort and pager links on a tag page use the same `ledgerQuery.values()` helpers as the ledger, which currently build `/entries?...&tag=<slug>`; the page stays correct if those helpers later take a page base path, because the tag is carried in the query either way.

9. **Tag management is editor work, tag deletion is owner work**: `GET /admin/tags` sits behind `requireAuth`; `POST /admin/tags` (create) and `POST /admin/tags/{id}` (rename, recolour) sit behind `withCSRF`; `POST /admin/tags/{id}/delete` sits behind `withOwnerCSRF`, matching the owner-only entry delete because it destroys assignments for every entry at once. The page shows a `live` count (entries with `deleted_at IS NULL`) and a `total` count (all join rows, trash included), and the delete form states the `total` in its confirmation, because that is the number of entries that lose the tag. Colour input is `<input type="color">` with server-side `#RRGGBB` validation, so a hand-crafted post cannot store arbitrary text.

10. **Audit names follow the existing vocabulary**: `tag.create` and `tag.delete` use the tag id as subject and `name=<name>` as detail; `tag.rename` and `tag.color` use the tag id and `old=... new=...`; `entry.tags` uses the entry id and the sorted list of resulting slugs, written even when the set is cleared. Every write goes through `auditAs`, so the audit page's action filter can isolate them and the timestamp ordering matches `entry.update`.

11. **Tagging does not touch the dedupe rule, and the specs say so**: `idx_entries_word_meaning` is unchanged, so a spelling and correction pair still exists at most once and tags can only distinguish kinds of slip, never count repeated attempts. A tag's count is therefore a count of entries, `unique_words` stays close to `total_entries`, and a per-tag "repeated slip" figure would be misleading; none is produced or displayed.

12. **The recap lives at `/y/{yyyy}`**: the prefix is unused by the router, the segment is four digits so it cannot be confused with `/e/{id}`, it does not collide with the planned `/p/{person}` pages, and it reads as "year" without claiming the `/stats` hierarchy that `/stats/{year}` would. `?year=` already means the ledger filter, so a query-string recap would be ambiguous.

13. **Recap figures are computed on read with fixed tie-breakers**: `YearReview(ctx, year)` returns an aggregate row (count, first and last `created_at`, photo count), the twelve month buckets, the top five persons, the longest misspelling and the first and last entries. The first and last entries come from `ListEntries` with `Year`, `PerPage: 1` and `created_at asc`/`desc`, so visibility and ordering stay in one place; the longest misspelling needs its own query because no list sort orders by length, and it uses `ORDER BY length(word) DESC, created_at ASC, id ASC LIMIT 1` with `word <> ''` and `deleted_at IS NULL`, where SQLite `length()` counts characters for text. Ties are broken deterministically: busiest month takes the earliest month, top persons take count descending then `person COLLATE NOCASE` ascending, and the longest misspelling takes rune length descending then the earliest `created_at` then the lowest id. Photo-only entries have an empty `word` and are excluded from the longest-misspelling figure rather than winning at length zero. The photo ratio uses the same rounded integer formula as `buildStatsPage`.

14. **Caching hashes the computed view**: unlike an append-only feed, a year page changes when an entry in that year is edited, trashed or restored without its id changing, so the ETag is `"year-<yyyy>-<first 16 hex of sha256 over the figures>"` and `Cache-Control: public, max-age=300` because a recap changes rarely. A matching `If-None-Match` is answered with 304 and no body using the existing `etagMatches`. 404 responses carry no ETag. All absolute URLs, including the canonical and sitemap entries, go through `absoluteURL`, so `PUBLIC_BASE_URL` wins behind a proxy.

15. **Accessibility reuses the `/stats` pattern and avoids a new violation**: the recap renders a twelve-month bar chart in a `figure` marked `aria-hidden="true"` with a sibling `<table class="visually-hidden">` captioned "Entries per month in &lt;year&gt;", and the top-persons ranking gets the same treatment captioned "Slips per person in &lt;year&gt;". The `/stats` chart's bars stay `aria-hidden`, so the recap links are a separate `nav aria-label="Year in review"` under the figure instead of links inside hidden content, which would be mouse-only. Years with a zero count are not linked, because `/y/{yyyy}` would 404 for them.

## Risks / Trade-offs

- **[Seed taxonomy does not fit the committee's usage]** -> the five seeds are ordinary tags: an admin renames, recolours or deletes them, the migration never runs again, and no entry is auto-tagged.
- **[Deleting a tag destroys context for many entries]** -> deletion is owner-only, behind CSRF, states the total number of entries that lose the tag, and leaves an audit row; the alternative, a soft-deleted tag, would need a visibility rule on every read.
- **[Tag filtering adds a subquery per tag]** -> each `EXISTS` is served by `idx_entry_tags_tag` (tag id first, entry id second), the composite key serves the entry side, and the ledger holds hundreds of rows, so a full scan would still be acceptable.
- **[Two URLs for the same tag view]** -> `/tags/{slug}` is canonical and in the sitemap, `/entries?tag=` is `noindex,follow` with no canonical link, and the sitemap never lists query-string URLs, so the crawlable tag document is unambiguous.
- **[Tag chips cost an extra query per page]** -> `TagsByEntry` fetches every tag for the visible page in one statement, so the ledger adds exactly one query regardless of page size.
- **[A year page can 404 after the last entry of that year is trashed]** -> the `/stats` link is emitted only for years whose count is above zero, and the 404 uses the existing not-found page so a stale link degrades to a normal error rather than an empty page with zeroes.
- **[ETag cost on every recap request]** -> hashing a handful of figures costs less than the SQL behind them, and a 304 still saves the full render.
- **[`YearReview` reuses `ListEntries` twice, which each count first]** -> four small queries per uncached recap; the recap is cached for 300 seconds and the table is small, and reusing the builder avoids a second visibility rule that could drift from `ledgerFilter`.
- **[Shared template and store surfaces with the planned browse change]** -> `add-ledger-browse` also edits `base.html`, `partials.html`, `handleSitemap`, `feed.go` and `internal/store/store.go`, so the two changes must be applied in sequence and the toolbar and sitemap hunks reconciled by hand; this change keeps its tag plumbing additive (hidden inputs, new clauses) to keep that merge mechanical.
