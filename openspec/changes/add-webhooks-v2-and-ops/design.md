## Context

The server is one Go binary with `net/http`, embedded SQLite (modernc, WAL, four connections) and server-rendered templates. `internal/webhook` has a `Dispatcher` that resolves one `config.Webhook` per send, marshals `webhook.Payload`, signs it with HMAC-SHA256 in `X-VanDyke-Signature`, POSTs it with a 5 second client timeout (`internal/webhook/webhook.go:144`) and reads at most 4 KiB of the response (`internal/webhook/webhook.go:160`). It is called fire-and-forget from the web create handler (`internal/web/web.go:562`) and the API create handler (`internal/httpapi/api.go:210`). There is no persistence, retry or log of any attempt.

The ledger lifecycle is now: `CreateEntry` (`internal/store/store.go:887`), `UpdateEntry` (`:1817`), `SoftDeleteEntries` (`:1920`), `RestoreEntries` (`:1958`) and `PurgeEntries` (`:1997`). Trashed rows keep their `(word, meaning)` slot and are excluded from public reads. `ApplyImport` (`internal/store/export.go:201`) can insert or replace up to 20,000 rows in one transaction. Settings resolve as persisted override first, then environment (`internal/settings/settings.go:169`). Admin pages use `requireAuth`, `requireOwner`, `withCSRF` and `withOwnerCSRF` (`internal/admin/admin.go:169-227`), and mutations call `recordAudit` (`internal/admin/audit.go:32`). The process has no scheduler; `main` only runs the listener and waits for `SIGINT`/`SIGTERM` (`cmd/vandyke/main.go:95-118`).

Endpoint URLs are supplied by an administrator, so outbound requests are an SSRF surface on a service that is normally deployed on a LAN alongside Home Assistant, ntfy and similar targets.

## Goals / Non-Goals

**Goals:**
- Deliver five entry lifecycle events to multiple independent endpoints, each with its own secret, event subscription and formatting preset.
- Preserve current single-target deployments and the existing generic payload and signature without a data migration.
- Retry transient failures durably with bounded memory and a lifecycle that starts and stops with the process.
- Give an operator one page to manage endpoints, test one, inspect the delivery log, retry a delivery and prune history.
- Expose entry, request, rate-limit and webhook state as Prometheus text without adding a dependency.
- Add a readiness probe that verifies SQLite and migrations, leaving liveness unchanged.

**Non-Goals:**
- Exactly-once delivery, ordering guarantees or inbound webhooks.
- Per-entry or per-field subscriptions, templating languages or custom headers beyond the signature.
- OpenTelemetry, tracing, push gateways, pprof, per-request log shipping or changing `/healthz`.
- Encrypting secrets at rest or per-endpoint RBAC beyond the existing owner/editor split.
- A general-purpose scheduler.

## Decisions

1. **Two tables own configuration and history.** `013_webhook_endpoints.sql` creates:

   ```sql
   CREATE TABLE webhook_endpoints (
       id            INTEGER PRIMARY KEY AUTOINCREMENT,
       name          TEXT NOT NULL,
       url           TEXT NOT NULL,
       secret        TEXT NOT NULL DEFAULT '',
       enabled       INTEGER NOT NULL DEFAULT 1,
       events        TEXT NOT NULL DEFAULT 'entry.created',
       preset        TEXT NOT NULL DEFAULT 'generic',
       allow_private INTEGER NOT NULL DEFAULT 0,
       created_at    TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
       updated_at    TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
   );
   CREATE UNIQUE INDEX webhook_endpoints_name ON webhook_endpoints (name COLLATE NOCASE);
   CREATE INDEX webhook_endpoints_enabled ON webhook_endpoints (enabled);

   CREATE TABLE webhook_deliveries (
       id              INTEGER PRIMARY KEY AUTOINCREMENT,
       endpoint_id     INTEGER REFERENCES webhook_endpoints (id) ON DELETE CASCADE,
       event           TEXT NOT NULL,
       entry_id        INTEGER,
       status          TEXT NOT NULL DEFAULT 'pending',
       attempts        INTEGER NOT NULL DEFAULT 0,
       last_status     INTEGER,
       last_error      TEXT NOT NULL DEFAULT '',
       next_attempt_at TEXT,
       payload         TEXT NOT NULL,
       created_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
       updated_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
   );
   CREATE INDEX webhook_deliveries_due ON webhook_deliveries (status, next_attempt_at);
   CREATE INDEX webhook_deliveries_endpoint ON webhook_deliveries (endpoint_id, created_at);
   CREATE INDEX webhook_deliveries_created_at ON webhook_deliveries (created_at);
   ```

   `events` is a comma-separated, sorted list of the five event names; there is no query by event, so a join table would add writes without a reader. `entry_id` deliberately has no foreign key: purging an entry must not erase the evidence that a purge event was delivered. `endpoint_id` is nullable so the legacy environment target can record deliveries without a synthetic row. `payload` stores the generic event envelope only while the row is pending or failed, so a retry after a purge can still send the identity it was created with; it is cleared when the row reaches `delivered` or `cancelled`. Endpoint count is capped at 20 and each event list must contain at least one known event.

2. **The store returns changed rows; handlers emit events.** Each mutating method captures the rows it actually changes inside its transaction and returns those rows instead of only a count, so the slice length is the count: `SoftDeleteEntries` selects live rows before the update, `RestoreEntries` selects trashed rows, `PurgeEntries` selects the rows before deleting, and `UpdateEntry` expands the row it already loads for `created_at` and photo state into a full previous snapshot. Handlers then call one `webhook.Emit` helper with the request context. This keeps delivery, formatting and absolute URLs out of the persistence layer, and it makes bulk idempotency exact: a delete of an id that is already trashed emits nothing. `CreateEntry` already returns the row. The store stays usable in tests with no event sink.

3. **One event per entry, including bulk actions.** A batch emit reads the engine's in-memory endpoint snapshot once and fans every changed row out to the subscribed endpoints, so a bulk delete, restore or purge of 100 ids emits at most 100 events per subscribed endpoint without touching the database on the request path. The shape is identical to a single-entry event, so a receiver never has to understand a second aggregate schema. With the endpoint cap of 20 the worst burst is 2,000 queue entries, which the queue cap and drop counter make explicit rather than growing memory. An aggregate event was rejected because it makes `id` meaningless and forces every consumer to implement two code paths.

4. **Import emits no events.** `ApplyImport` is a bulk migration/restore path for up to 20,000 rows; emitting per-row events would flood a queue that is deliberately small or deliver an arbitrary prefix before dropping the rest. Receivers that need to reconcile after an import already have the export endpoint and the ledger API. This exception is documented in the requirement so `entry.created` is not misread as a complete change log.

5. **`entry.updated` carries a bounded diff.** The payload adds `occurred_at` and a `changes` object keyed by `word`, `meaning`, `person`, `created_at` and `photo`; each value is `{"from": ..., "to": ...}`. A boolean `photo` would report a replacement as true to true, so `photo` carries the previous and new `entry_photos.sha256` of the original photo truncated to 12 hex characters, or null when the entry has no photo; the display and thumb variants are derived and are not part of the identity. Unchanged fields are omitted, and an edit that changes nothing emits no event. A full snapshot without the diff would force every mirror to diff two payloads; a diff without the snapshot would force a second fetch for the current values. Both are cheap here because the entry is at most a few hundred bytes.

6. **The generic envelope is frozen for `entry.created`.** The `generic` body for `entry.created` is exactly the seven existing keys `event`, `id`, `word`, `meaning`, `person`, `created_at` and `url`, with the same RFC 3339 timestamps and absolute `{base}/e/{id}` URL. New event types use the same seven keys plus `occurred_at`, and an edit to a trashed row adds `deleted_at` so a receiver can tell it apart from a live edit; `entry.deleted` and `entry.purged` always carry `deleted_at` because their snapshot is trashed, while `entry.restored` does not. `entry.updated` also adds `changes`. `entry.created` gains no field, so an existing receiver or a byte-level test sees no change. Ordering in the JSON object is not part of the contract.

7. **Presets render the body, then the body is signed.** `generic` sends the envelope as JSON. `discord` sends `content` plus one embed with required `title`, `description`, `url` and `timestamp`, and sets `allowed_mentions.parse` to an empty list so a word containing `@everyone` cannot ping a channel. `slack` sends a `text` fallback plus one `section` block whose `text.type` is `mrkdwn`, with `&`, `<` and `>` escaped so an entry cannot inject `<!channel>`. An entry may have an empty word or meaning when it carries a photo, and Discord rejects an empty embed title, so the preset substitutes `Entry #<id>` for an empty title and the permalink for an empty description; the Slack text and block use the same fallbacks. Rendering happens per endpoint on every attempt, and HMAC is computed over the exact rendered bytes with that endpoint's secret, so the existing `sha256=<hex>` verification works for all three presets. A render error is terminal, not retryable.

8. **The legacy target is a synthesized endpoint, not a startup row.** When `webhook.url` or `LEDGER_WEBHOOK_URL` resolves to a non-empty URL and no enabled persisted endpoint exists, the engine treats it as an in-memory endpoint named "Environment default" with the generic preset and only `entry.created`. Its deliveries are recorded with `endpoint_id` null. The engine keeps a snapshot of the at most 20 endpoint rows plus this synthesized endpoint, built at startup and rebuilt after every endpoint mutation; the legacy URL and secret are read from the existing in-memory settings resolver, so a settings change applies immediately. This preserves every existing deployment without writing environment configuration into SQLite, without resurrecting a row an operator deleted, and without making environment changes require a database edit. If any persisted endpoint is enabled, the legacy target is suppressed so a migration cannot double-deliver. `POST /admin/webhooks/adopt` copies the effective URL and secret into a real endpoint so the secret does not have to be retyped; the suppression rule then hides the legacy path while that endpoint stays enabled. The existing `/admin/settings` form and `POST /admin/settings/webhook/test` keep operating on the legacy target and are labelled as legacy.

9. **The delivery engine is the first background loop.** `main` constructs one `webhook.Engine` after the store and settings and passes that same instance to the web, API and admin constructors, replacing the three independent `webhook.New` calls currently made in `web.New`, `httpapi.New` and `admin.New`; it starts the engine before `ListenAndServe` and calls `Close` on shutdown before the deferred `st.Close` can run. The engine holds an atomic snapshot of the endpoint configuration, rebuilt at `Start` and after every endpoint mutation, so `EmitBatch` only loads the snapshot, stamps `occurred_at`, and performs a non-blocking channel send; the job carries the entry snapshot, event type and resolved endpoint settings, while JSON encoding, preset rendering, signing and persistence happen in the worker, so no database read, rendering, DNS or network I/O happens on the request path. The retry tick rebuilds the snapshot every 10 seconds as well, which self-heals a failed reload. The queue holds 1,024 new jobs, and the same four delivery workers serve both those jobs and due retries; the retry ticker bypasses the new-event queue so a full queue cannot starve retries, and the global in-flight cap stays at four. A 10 second retry ticker drains due rows and an hourly ticker prunes history. Enqueue is non-blocking: when the channel is full the event is dropped, `vandyke_webhook_dropped_total` is incremented and a warning records the event and entry id. A job is persisted as a `webhook_deliveries` row with `status = 'pending'` and `next_attempt_at` set to now when a worker first picks it up, so a crash after the insert still leaves a due row and retry state survives a restart; a crash before pickup loses that attempt. Before persisting, the worker re-reads the endpoint and discards the job if the row is gone or disabled, which avoids an insert against a cascaded foreign key and avoids sending for an endpoint that was switched off after enqueue. That is the same best-effort boundary the current fire-and-forget dispatcher has, now with an explicit counter instead of silence. The admin test fire is a separate synchronous request and does not consume the four-worker budget. The memory bound is the queue cap times a small envelope: entry fields are capped at 200, 500 and 100 characters, so 1,024 jobs hold roughly 1 MiB of payload rather than a ledger-sized backlog.

10. **Retries are persisted, jittered and bounded.** A 2xx marks the delivery `delivered`. Transport errors, timeouts, 408, 425, 429 and 5xx are retryable; any other response is a permanent failure. The delay after attempt `n` is a random value in `[0, min(5s * 2^(n-1), 1h)]` (full jitter), stored in `next_attempt_at`. The maximum is 8 attempts. A terminal row clears `next_attempt_at`. The retry ticker claims up to 100 due rows per pass, so a large backlog drains in bounded batches. Pending rows for a disabled or deleted endpoint are marked `cancelled` instead of being sent. Ordering between events is not guaranteed; the envelope's `occurred_at` and `id` let receivers order their own view.

11. **"Retry now" is an explicit one-shot.** It sets `status = 'pending'` and `next_attempt_at` to now but leaves `attempts` unchanged. The attempt cap is applied when scheduling the next retry, not when a row is already pending, so an operator always gets one attempt after asking. Each manual retry writes an audit row.

12. **Retention is age-based and automatic.** The hourly prune deletes `delivered` and `cancelled` rows older than 7 days and `failed` rows older than 30 days. Pending rows are never pruned. The admin page offers the same prune as an explicit owner action and reports the deleted count. The deliveries table is therefore bounded by traffic over the retention window, not by ledger size.

13. **A purge erases delivered copies of its payload.** `PurgeEntries` deletes terminal `webhook_deliveries` rows whose `entry_id` is one of the purged ids, so a delivered or cancelled copy of the entry's word and meaning does not outlive the purge. Pending and failed rows remain because they exist to notify about the purge itself, and the retention rules above bound them: a delivered row clears its payload immediately, a failed row keeps it only so "retry now" can work, and the operator can prune failed rows explicitly.

14. **Admin routes follow the existing role split.** `GET /admin/webhooks` uses `requireAuth`. Create, edit, enable/disable, adopt and per-endpoint test use `withCSRF`, matching `POST /admin/settings`; editors already control `webhook.url`, so endpoint configuration adds no new privilege. Delete and prune use `withOwnerCSRF`, matching purge and admin management. `allow_private` may only be turned on or off by an owner; an editor's submission leaves the stored value unchanged. Every change calls `auditAs` with the endpoint id, the changed field names and the host, never the URL query, path token or secret. Action names are `webhook.endpoint.create`, `webhook.endpoint.update`, `webhook.endpoint.delete`, `webhook.endpoint.enable`, `webhook.endpoint.disable`, `webhook.endpoint.adopt`, `webhook.test`, `webhook.delivery.retry` and `webhook.prune`.

15. **SSRF is denied by default, with a realistic LAN opt-in.** The scheme must be `http` or `https`, the URL must have a host and no userinfo, and the host must not be an IP literal in a denied range unless the endpoint has `allow_private` and the range is loopback or private. Denied ranges are loopback, RFC 1918, IPv6 unique-local, carrier-grade NAT (100.64.0.0/10, which covers Tailscale), link-local (including `169.254.169.254`), unspecified, multicast and IPv4-mapped equivalents. `allow_private` permits loopback and private ranges, including carrier-grade NAT, for LAN receivers such as Home Assistant, ntfy or a tailnet address, but never link-local, unspecified or multicast. The synthesized legacy endpoint is treated as `allow_private` because it predates this control and an operator set it through the environment or settings; it was already allowed to reach a LAN address, and link-local remains blocked. The check runs at save time and again at delivery time: the dialer resolves the host, rejects the attempt if any returned address is disallowed, and dials the validated address while keeping the URL host for TLS SNI and certificate verification. A DNS failure at save time does not block the save because a LAN target may be temporarily offline; the check runs again before the attempt. Redirects are not followed, the total attempt timeout is 5 seconds, and at most 4 KiB of the response body is read and discarded.

16. **Metrics are hand-written in the standard library.** `internal/metrics` holds atomic counters, a mutex-guarded histogram set and an `http.Handler` that writes text exposition version 0.0.4 with `# HELP` and `# TYPE` lines, `Content-Type: text/plain; version=0.0.4; charset=utf-8` and no timestamps. Counters are process-local and reset on restart; database-backed gauges reflect the current state. `vandyke_entries_total` is a gauge despite the `_total` name because it is a current count, not a monotonic counter. DB-backed gauges are read at scrape time under a 2 second context; if the query fails, `vandyke_db_up` is 0, DB-dependent series are omitted, the failure is logged and the endpoint still answers 200 so process metrics remain scrapeable. Histogram buckets are 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s, 10s and `+Inf`. No new module is added to `go.mod`.

17. **Route labels come from the mux pattern, never the path.** The metrics middleware records `method` and `route`, where route is `r.Pattern` such as `GET /api/v1/entries/{id}`, or `unmatched` when no pattern matched. It sits between the request logger and the panic recovery (`SecurityHeaders → RequestLogger → Metrics → Recover → mux`) so a recovered panic is still counted as a 500 and the matched pattern survives. The raw path is never a label: `/e/123` would create one series per entry and leak ids into a scrape that may be broadly readable. Status is the exact three-digit code, which is a small fixed set. For the same reason no endpoint URL, entry id or person is a label anywhere.

18. **Readiness is separate from liveness.** `GET /readyz` runs `SELECT 1` and compares the versions in `schema_migrations` with the embedded migration list, with a 2 second timeout. It returns 200 and `{"status":"ready","checks":{"database":"ok","migrations":"ok"}}`, or 503 with `"unavailable"` and the coarse failing check. The body never contains the DSN, the database path, an error string, a version string or a credential. `/healthz` keeps its current always-200 body so existing probes do not change meaning.

19. **`/metrics` is public unless a token is configured.** This is a LAN self-hosted app whose ledger pages and JSON API are already public, and Prometheus commonly scrapes from another host or container, so loopback-only would make the endpoint useless. When `METRICS_TOKEN` is set, `/metrics` requires `Authorization: Bearer <token>` compared in constant time and returns 401 otherwise; the token is never logged, and operators on an untrusted network can also restrict the endpoint at the reverse proxy. `/readyz` is never gated because probes must work without credentials and it exposes only a coarse readiness state. Neither endpoint is cached.

## Risks / Trade-offs

- **[Queue drops under a bulk burst]** -> The cap is 1,024 jobs and the drop counter is exported; a 100-id purge with 20 endpoints can exceed it, and those lost events are visible in `vandyke_webhook_dropped_total` rather than silently queued.
- **[A crash before a worker persists a job loses that event]** -> This is the existing best-effort boundary; once a row exists, retries survive restarts, and receivers can reconcile from the ledger API or export.
- **[At-least-once duplicates after a retry]** -> Receivers must de-duplicate on `event` plus `id`, plus `occurred_at` where the payload carries it, which is documented; exactly-once is a non-goal.
- **[Secrets are stored in plaintext in SQLite]** -> The database file permissions remain the boundary, matching today's `settings` table; the UI never renders a secret, and audit and logs record only whether one changed.
- **[A purged entry survives in a delivery payload]** -> A delivered or cancelled row clears its payload immediately and the purge deletes terminal delivery rows for the purged ids; only a pending or failed notification keeps the text, because it exists to announce the purge, and the operator can prune it.
- **[A URL can embed a provider token]** -> Discord and Slack URLs contain a token in the path; the list view masks the path and query, logs and audit rows record only the host, and only the authenticated edit form shows the stored value.
- **[Private-target opt-in widens the SSRF surface]** -> The default denies loopback and private ranges; only an owner can set `allow_private`, link-local and metadata addresses stay denied, redirects are not followed, and DNS is re-checked at dial time.
- **[Metrics expose usage metadata]** -> Only counts, route patterns, durations, version and DB size are exported, never entry text, ids, persons or endpoint URLs; `METRICS_TOKEN` or a proxy ACL can gate the endpoint.
- **[A scrape adds database work]** -> DB gauges run a few small queries per scrape under a 2 second timeout; a typical 15 to 60 second scrape interval makes this negligible, and a failure only drops the DB series.
- **[Per-endpoint preset changes alter retry bodies]** -> The generic envelope is stored, but the rendered body can change between attempts if an operator edits the preset; this is acceptable because the event data is unchanged and the signature always covers the body actually sent.
- **[An endpoint edit races with queued events]** -> A job already in the queue may use the URL, preset and secret it was emitted with, while the next event uses the new configuration; the window is bounded by the queue and the worker re-checks that the endpoint still exists and is enabled.
- **[A failed snapshot reload can double-deliver]** -> After the first persisted endpoint is created, a failed reload can leave the legacy target active in the old snapshot for up to one retry tick; the window is bounded at 10 seconds, the failure is logged, and the reload is retried on every tick.
- **[Migration ordering with the other pending change]** -> This change owns `013`; the parallel change owns `014`. A database that applies `014` first still applies `013` on the next start because migrations are keyed by filename, but the two changes must not be archived with the numbers swapped.
- **[The legacy path can confuse operators]** -> The admin page shows the synthesized endpoint as read-only and explains that a persisted endpoint suppresses it; the adopt action is the intended migration step. Disabling the last persisted endpoint reactivates the legacy target if an environment URL is still set, so the page marks that row active and the settings page says so.
- **[This change modifies a capability from an unarchived change]** -> `ledger-webhooks` is introduced by `add-activity-feed-webhooks`; archive that change before this one, or apply its `ADDED` requirements before these `MODIFIED` ones, so the delta has a baseline.
